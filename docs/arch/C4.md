# C4 Model Documentation

## 1. Context

This project is a local banking simulator focused on core-banking concepts for funds transfer and lending. It offers a small REST API for interacting with account records, transfer operations, business routines, and a simple simulated loan workflow. The application is designed for local development and demonstration, not for a production-grade banking system.

The system is intentionally scoped to a single deployable Java/Spring Boot application backed by an in-memory H2 database for fast local iteration. The runtime is clearly separated from any real Temenos environment or proprietary T24 implementation.

### 3.2 Component list

- AccountController
  - exposes account and transfer endpoints
  - translates requests/responses to DTOs
  - returns consistent validation and business errors

- AccountService
  - validates inputs and business rules
  - performs account lookup and transfer coordination
  - is the main application use-case orchestrator

  - enforces basic domain semantics

  - converts validation and business exceptions to structured error payloads

## 5. Dynamic View

### Transfer scenario

```text
Developer/User -> AccountController: POST /api/v1/transfers
AccountController -> AccountService: transfer(request)
AccountService -> AccountRepository: find source and destination accounts
AccountService -> AccountService: validate currency, status, balance, and amount
AccountService -> AccountRepository: save debited and credited balances
AccountRepository -> H2: commit updated account rows
AccountService -> AccountController: TransferResponse
AccountController -> User: HTTP 200 + transfer result
```

### Business validation flow

1. Request is received by the controller
2. Validation annotations check required fields and positive amount
3. Service enforces account state and currency rules
4. Transaction updates are applied atomically in the repository layer
5. A response is returned with success or business-rule error details

## 7. Cross-cutting concerns

### Security
- Synthetic demo data only
- No production credentials or secrets stored in the repo
- Validation and error responses avoid exposing infrastructure internals

### Observability
- Spring Boot Actuator exposes health endpoints
- Logs can be used to inspect transfer and service activity
- Requests are simple to trace in local testing

### Testability
- Unit tests target service behavior and validation scenarios
- The app can run without Docker, which makes test execution faster and simpler

### Reliability
- Business-validation rules are enforced before financial updates
- Repository operations are expected to run transactionally in the application service flow
- In-memory H2 is intentionally a fast local substitute, not a production persistence solution

---

## 8. Summary

The C4 model for this project shows a simple, understandable architecture centered on a single Spring Boot application and a local H2 database. This keeps the code easy to run, easy to test, and easy to review while still demonstrating core-banking concepts such as account validation, transfer logic, and simulated financial rules.
